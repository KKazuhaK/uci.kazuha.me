2. 文档作为向量

第 7 周以 tf-idf 收尾（第 7 周第 18.3 节）：wt,d=(1+log⁡10tft,d)×log⁡10(N/dft)w_{t,d} = (1 + \log_{10} \mathrm{tf}_{t,d}) \times \log_{10}(N/\mathrm{df}_t)wt,d​=(1+log10​tft,d​)×log10​(N/dft​)，这是最著名的加权方案，它随词项在文档中的出现次数增加而增大，也随它在集合中的稀有程度增加而增大（L22 p4 回顾）。

文档作为向量（L21 p6–10）：

  • 我们有一个 ∣V∣|V|∣V∣ 维向量空间（∣V∣|V|∣V∣ 为词表大小）。
  • 词项是空间的坐标轴。
  • 文档是这个空间中的点或向量。
  • 维度极高：对网络搜索引擎而言可达数千万维。
  • 极其稀疏：大多数分量为零（一个网页只用到词表的极小一部分）。

💡 关键见解：文档向量从来不会被存成 ∣V∣|V|∣V∣ 个数字——它的非零分量恰好就是它的 postings。

3. 查询作为向量，以及为什么不用欧氏距离

查询作为向量（L21 p11–14 · L22 p5）：

  • 关键思想 1：对查询做同样的事——把它们表示为同一空间中的向量。
  • 关键思想 2：在这个空间中，按文档与查询的接近程度给文档排序。接近程度 = 向量的相似度；接近程度 ≈ 距离的倒数。
  • 原因：我们希望摆脱非此即彼的布尔模型，转而把更相关的文档排在更不相关的文档之前（第 7 周第 14 节）。

把接近程度形式化（L21 p15–18）。最先想到的是两点之间的距离（即两个向量终点之间的距离）：欧氏距离？ 这是一个坏主意，因为欧氏距离对长度不同的向量会很大——而查询和文档的长度通常相差很大。

示意图（L21 p19）：两个坐标轴，JEALOUS（x）与 GOSSIP（y），取值都在 0 到 1 之间。d1d_1d1​ 几乎笔直向上（主要是 gossip），d3d_3d3​ 几乎水平（主要是 jealous），而 qqq 与 d2d_2d2​ 指向几乎相同的方向（两个词项，比例相近）——但 d2d_2d2​ 是一根长得多的箭头，伸出了单位正方形之外。qqq 与 d2d_2d2​ 之间的欧氏距离很大，尽管 qqq 与 d2d_2d2​ 中词项的分布非常相似。

L22 p7 用排序重复了同一个要点：在 term1/term2 坐标轴上，qqq 位于 (1, 1) 附近。d1d_1d1​ 位于过原点、与 qqq 同一条直线上、更远的位置；而 d2d_2d2​ 作为一个点离 qqq 更近，但方向更陡。按欧氏 tf-idf：d2,d1d_2, d_1d2​,d1​。按余弦：d1,d2d_1, d_2d1​,d2​。

⚠️ 易错点：“离得最近”和“方向最相似”是两个不同的问题。一篇与查询主题完全相符的长文档，按欧氏距离衡量，离一个 3 词的查询很远。向量空间模型按方向排序。

4. 用夹角：余弦相似度

思想实验（L21 p20–24）：取一个文档 ddd，把它接到自身后面；记作 d′d'd′。

  • “从语义上”看，ddd 与 d′d'd′ 有相同的内容。
  • 它们之间的欧氏距离可能相当大——很糟！
  • 它们之间的夹角为 0，对应最大相似度——很好！

关键思想：按文档与查询之间的夹角给文档排序。

从夹角到余弦（L21 p25–26）。在 [0°,180°][0°, 180°][0°,180°] 上，余弦是单调递减的函数（幻灯片画的是从 0° 到 360° 的 cos⁡\coscos：0° 时为 1，90° 时为 0，180° 时为 −1，360° 时回到 1）。因此按夹角排序与按余弦排序是等价的。幻灯片把“夹角递减的顺序”与“余弦递增的顺序”配对——这个等价是正确的，但我们想要的排序是另一对：夹角递增 = 余弦递减，最好的文档排在最前。

cosine(query, document)（L21 p27 · L22 p6）：

cos⁡(q⃗,d⃗)=q⃗⋅d⃗∣q⃗∣ ∣d⃗∣=q⃗∣q⃗∣⋅d⃗∣d⃗∣=∑i=1∣V∣qidi∑i=1∣V∣qi2 ∑i=1∣V∣di2\cos(\vec q, \vec d) = \frac{\vec q \cdot \vec d}{\lvert\vec q\rvert\,\lvert\vec d\rvert} = \frac{\vec q}{\lvert\vec q\rvert} \cdot \frac{\vec d}{\lvert\vec d\rvert} = \frac{\sum_{i=1}^{|V|} q_i d_i}{\sqrt{\sum_{i=1}^{|V|} q_i^2}\,\sqrt{\sum_{i=1}^{|V|} d_i^2}}cos(q​,d)=∣q​∣∣d∣q​⋅d​=∣q​∣q​​⋅∣d∣d​=∑i=1∣V∣​qi2​​∑i=1∣V∣​di2​​∑i=1∣V∣​qi​di​​

qiq_iqi​ 是词项 iii 在查询中的 tf-idf 权重，did_idi​ 是词项 iii 在文档中的 tf-idf 权重。分子是点积；除以两个向量的长度后，两个向量都变成了单位向量。cos⁡(q⃗,d⃗)\cos(\vec q, \vec d)cos(q​,d) 就是 qqq 与 ddd 的余弦相似度——等价地说，就是它们夹角的余弦。

5. 长度归一化

向量的长度归一化是用它的 L2L_2L2​ 范数去除每个分量（L21 p28–30）：

∥x⃗∥2=∑ixi2\lVert\vec x\rVert_2 = \sqrt{\sum_i x_i^2}∥x∥2​=i∑​xi2​​
  • 除以 L2L_2L2​ 范数后，它成为一个单位向量——即单位超球面表面上的一个点。
  • 对 ddd 与 d′d'd′（ddd 接到自身后面）的影响：长度归一化之后，它们是完全相同的向量。
  • 长文档与短文档的权重现在可以相互比较了。

对于长度归一化的向量，余弦（L21 p31）就是简单的点积（数量积）：

6. 计算余弦分数

算法（L21 p33 · L22 p9，后者高亮了最后一行 “Top K components of Scores[]”）：

CosineScore(q)
 1  float Scores[N] = 0
 2  float Length[N]
 3  for each query term t
 4  do calculate w_t,q and fetch postings list for t
 5       for each pair(d, tf_t,d) in postings list
 6       do Scores[d] += w_t,d × w_t,q
 7  Read the array Length
 8  for each d
 9  do Scores[d] = Scores[d] / Length[d]
10  return Top K components of Scores[]
  • 它是按词项处理的（第 7 周第 11 节）：Scores 就是累加器，每次填充一个 postings 列表。
  • 只有包含至少一个查询词项的文档才会得到非零分数——读取的只有 postings 列表。
  • Length[d] 在建索引时计算，这里只是读取（第 7 行）；最后的除法（第 9 行）是余弦中关于文档的那一半。查询的长度对每个文档都相同，所以不会改变排序。
  • 第 10 行就是第 10 节要解决的问题：不必对所有结果排序，直接得到前 K 个。

下面用 Python 实现同样的步骤，取 L21 的 lnc.ltc 例子（§7）：文档 car insurance auto insurance，查询 best car insurance：

import heapq
import math

# The lnc.ltc example (L21 p47-53): one document.
docs = {"d": "car insurance auto insurance".split()}
df = {"auto": 5000, "best": 50000,
      "car": 10000, "insurance": 1000}
N = 1_000_000

def log_tf(tf):
    return 1 + math.log10(tf) if tf > 0 else 0

# Index time: postings (d, tf) and Length[d] (lnc)
postings, length = {}, {}
for d, words in docs.items():
    counts = {t: words.count(t) for t in set(words)}
    for t, tf in counts.items():
        postings.setdefault(t, []).append((d, tf))
    length[d] = math.sqrt(sum(log_tf(tf) ** 2
                              for tf in counts.values()))

def cosine_score(query, K=10):
    q = {t: query.count(t) for t in set(query)}
    w_q = {t: log_tf(tf) * math.log10(N / df[t])
           for t, tf in q.items()}          # ltc ...
    q_len = math.sqrt(sum(w * w for w in w_q.values()))
    scores = {}                             # line 1
    for t, wtq in w_q.items():              # lines 3-4
        for d, tf in postings.get(t, []):   # line 5
            scores[d] = scores.get(d, 0) + \
                log_tf(tf) * wtq / q_len    # line 6
    for d in scores:                        # lines 7-9
        scores[d] /= length[d]
    return heapq.nlargest(K, scores.items(),
                          key=lambda x: x[1])  # line 10

print(round(length["d"], 2))
print([(d, round(s, 2)) for d, s in
       cosine_score("best car insurance".split())])
1.92
[('d', 0.8)]

文档长度 1.92 与分数 0.8 来自幻灯片（L21 p52–53）。（幻灯片上没有印出 NNN = 1,000,000；它是能复现其 idf 列的数值，例如 log⁡10(106/5000)=2.3\log_{10}(10^6/5000) = 2.3log10​(106/5000)=2.3。）

查询与文档的加权可以不同（L21 p43–46）：

  • 许多搜索引擎允许对查询和文档使用不同的加权。
  • SMART 记号用 ddd.qqq 表示引擎所用的组合——文档三个字母，查询三个字母，字母取自上表。

8. 向量空间排序的总结与扩展

总结——向量空间排序（L21 p54–56）：

  1. 把查询表示为加权的 tf-idf 向量。
  2. 把每个文档表示为加权的 tf-idf 向量。
  3. 计算查询向量与每个文档向量的余弦相似度分数。
  4. 按分数对文档相对于查询进行排序。
  5. 把前 K 个（例如 K = 10）返回给用户。

9. 高效的余弦排序

L22（“Scoring and result assembly”，打分与结果组装）提出了如何让第 6 节的算法变快的问题（L22 p10–17）：

  • 在集合中找出与查询“最近”的K 个文档 ⇒ 即查询与文档余弦中最大的 K 个。
  • 高效排序意味着两件事：高效地计算单个余弦，以及高效地选出最大的 K 个余弦值。
  • 能否不计算全部 N 个余弦就完成这件事？
  • 我们实际上是在为查询向量求解 K 近邻问题。一般来说，我们不知道如何在高维空间中高效地做到这一点——
  • 但对网络搜索而言我们不必如此：查询向量高度稀疏！ 对于短查询，这个问题是可以解决的，并且标准索引对此支持得很好（只需读取查询词项的少数几个 postings 列表）。

特殊情形——无权重查询（L22 p18）：对查询词项不加权——假设每个查询词项只出现一次。这样为了排序，你不需要对查询向量做归一化：每个文档的分数都除以同一个查询长度，这不会改变顺序。（因此 wt,q=1w_{t,q} = 1wt,q​=1，CosineScore 第 6 行只需累加 wt,dw_{t,d}wt,d​。）

10. 用堆选出前 K 个

选择与排序（L22 p19–21）：我们通常只想要余弦排序中的前 K 个文档，而不是集合中所有文档的全序。能否直接挑出余弦最高的 K 个文档？设 J 为余弦非零的文档数；我们要的是这 J 个中最好的 K 个。

使用堆（L22 p22）：

  • 一棵二叉树，其中每个节点的值大于其子节点的值（即最大堆；参见 ICS 46 第 10 讲第 9 节）。
  • 构建需要 2J 次操作，然后每个K 个“胜出者”可以在 2 log J 步内取出。
  • 当 J = 100 万、K = 100 时，这大约只是排序成本的 10%！

取以 2 为底的对数，排序需要 Jlog⁡2JJ \log_2 JJlog2​J 次比较：堆 =2J+2Klog⁡2J≈= 2J + 2K\log_2 J \approx=2J+2Klog2​J≈ 200 万，排序约 1990 万，比值为 0.10——即幻灯片上的 10%。（在 Python 中，§6 里的 heapq.nlargest(K, …) 正是做这件事。）

⚠️ 易错点：节省来自 K ≪ J：建堆是线性的，而 log⁡J\log JlogJ 只需付出 K 次。排序则要为每一个的 J 个文档付出 log⁡J\log JlogJ。

11. 余弦只是代理：近似的前 K 个

瓶颈（L22 p23–27）：打分中的主要计算瓶颈是余弦计算。能否避开所有这些计算？可以，但有时可能会算错：一个不在前 K 个中的文档可能会混进输出的 K 个文档列表。这是件很坏的事吗？

余弦相似度只是一个代理！（L22 p28–31）

  • 用户有一个任务，以及一个查询表述。
  • 余弦衡量的是文档与查询的匹配——而不是与任务的匹配。
  • 因此，余弦无论如何都只是用户满意度的一个代理。
  • 如果我们得到的 K 个文档列表，按余弦来看与前 K 个“接近”，它应该是可以接受的。

通用方法（L22 p32–35）：

  • 找一个候选集合 A，满足 K<∣A∣≪NK < |A| \ll NK<∣A∣≪N。
    • AAA 不一定包含前 K 个，
    • 但它包含前 K 个中的许多文档。
    • 返回 AAA 中的前 K 个文档。
  • 可以把 AAA 看作剪掉非候选者的结果。
  • 同样的方法也用于其他（非余弦）的打分函数。
  • 我们将看几种遵循这一思路的方案：本周看索引剪枝（§12）；champion 列表、分层索引及其余内容见第 9 周。

💡 关键见解：对比第 7 周的安全与不安全优化（第 7 周第 13 节）：从这里开始，一切都刻意是不安全的——用精确的前 K 个换取速度，这样做是合理的，因为精确的前 K 个从来都不是真正的目标。

12. 索引剪枝

基本的余弦算法本来就只考虑包含至少一个查询词项的文档（L22 p36–37）。把这一启发式进一步推广：

  1. 只考虑高 idf 的查询词项。
  2. 只考虑包含许多查询词项的文档。

只用高 idf 的查询词项（L22 p38–40）：对于 catcher in the rye 这样的查询，只累加 catcher 和 rye 的分数。直觉是：in 和 the 对分数贡献很小，因此基本不会改变排序。好处是：低 idf 词项的 postings 包含很多文档 → 这些（很多！！！）文档会被从候选集合 A 中剔除。

包含许多查询词项的文档（L22 p41–45，p47）：

  • 任何包含至少一个查询词项的文档，都是前 K 个输出列表的候选。
  • 对于多词项查询，只为包含若干个查询词项（甚至可能是全部词项！）的文档计算分数——比如四个中至少三个。
  • 这相当于对查询施加了一个“软合取”，这在网络搜索引擎（早期的 Google）上可以见到。
  • 如果限制太严，它可能最终得到的候选少于 K 个。可以在此之上再加一个启发式：可以迭代！（放宽到更少的词项）。
  • 很容易在 postings 遍历中实现。

例子：四个查询词项中的三个（L22 p46）：

词项 Postings
Antony 3 4 8 16 32 64 128
Brutus 2 4 8 16 32 64 128
Caesar 1 2 3 5 8 13 21 34
Calpurnia 13 16 32

只为文档 8、16 和 32 计算分数（即方框中的 postings）。如果只想向用户展示 2 个文档，这就够了；如果需要更多，就迭代，并同时为包含 2 个查询词项的文档计算分数。

⚠️ 易错点：“至少 3 个（共 4 个）”不是 AND——文档 8 缺少 Calpurnia，文档 16 缺少 Caesar，两者都会被打分。它是对文档出现在几个列表中的阈值判断，而按文档处理的遍历可以免费地数出这个次数。

必记的 5 件事

  1. 按夹角而非距离排序：余弦就是长度归一化的 tf-idf 向量的点积，因此一个文档和它的双倍副本是完全相同的。
  2. 文档在建索引时就做归一化（Length[d]）；查询的长度从不改变排序，因此无权重查询完全不需要归一化。
  3. SMART 的 ddd.qqq 把文档放在前面：lnc.ltc = 文档对数 tf + 余弦，无 idf；查询对数 tf + idf + 余弦。幻灯片例子的分数：0.8。
  4. CosineScore 是带累加器的按词项处理，它的最后一行是前 K 选择——堆胜过对全部 J 个已打分文档排序（J = 100 万、K = 100 时约为成本的 10%）。
  5. 余弦只是用户满意度的代理，因此近似的前 K 个是可以接受的：构造一个候选集合 A——例如用索引剪枝（只用高 idf 词项；保留四个中至少 3 个词项的文档，若太少则迭代）。
